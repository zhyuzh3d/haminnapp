# HaminnApp 开发工作区与正式版分叉的判定计划

版本 1.0，2026-09-30。本文件是 `haminnapp-unified-dev-workspace-plan.md` 的专题延伸，只处理一件事：

**当设备上的正式版被换成了另一个包，而本地还留着这个 happ 的开发工作区时，谁来做决定、依据什么做、什么时候才需要问用户。**

本计划只定义判定与询问，不定义备份实现，不提供版本回退流程。

## 一、问题

用户在设备上装了一个 happ，进入开发模式改成自己的版本；此后又装进了别人发来的包（或自己另一个版本），再次打开开发模式时，开发工作区是基于旧包的，设备正式版已经换人。

要求的底线是两条：

1. **不能丢用户还没落定的开发内容。**
2. **不能因此反复询问** —— 只在关键变更、确实可能导致开发内容被自动覆盖的时候才问。

## 二、为什么不能用版本号

版本号在两个方向都会骗人：

- 改了代码没升版 ⇒ 判成“没分歧”，静默覆盖；
- 本地第三段一直 +1，涨得比别人的包号还大 ⇒ 判成“我更新”，反过来覆盖别人的包。

别人的包号也可能只是计数基数不同（`0.1.10` 与 `0.1.100` 之间没有任何可比较的语义）。

**结论：版本号既不能证明内容一致，也不能证明谁更新。任何覆盖决定都不得以版本号为依据。** 这条与上位计划第二节“版本号不是内容一致性的证明”一致。

## 三、判定依据的分层

判定只能建立在“本机自己算出来的东西”上。包里自带的信息一律只作参考。

| 信息 | 谁生成 | 可信度 | 能否参与自动判定 |
| --- | --- | --- | --- |
| 包内容的指纹、体积、文件数 | **haminn 自己计算** | 客观事实 | **能**，唯一依据 |
| 包的来源通道、安装时间、装在哪台机 | 本机记录 | 客观事实 | **能** |
| 包自带的基线包、作者、打包日期、版本号 | 打包者写或工具生成 | **仅供参考** | **不能**，只用于展示 |

两条硬规则：

- **包自身的指纹不得采信包内声明，必须由接收方 haminn 自行计算。**
- **包声明的“基于哪个包”不可信**，只能用于向人展示；它不参与任何自动决定。

内容寻址还带来一个好处：**同一个指纹就是同一份代码，不必关心是谁传给你的。** 若别人发来的包恰好与你自己发过的某个版本内容完全相同，那就是同一份代码，不存在分歧。

## 四、代码现状（已核对，2026-09-30）

### 4.1 两份存储是分开的，安装包伤不到开发工作区

- 开发工作区在 `dev_workspaces` 表，主键 `app_id`（`registry/AppRegistry.kt:843-855`）：`base_release_id`、`generation`、`revision`、`tree_hash`、`dirty`。
- 正式版在 `releases` 表 + `instances.active_release_id`（`registry/AppRegistry.kt:29-70`）。
- 所有 happ 安装路径都汇聚到 `install/InstallCoordinator.kt` 的 `installZip`（`:224-245`），只写 `releases` 与 `instances`，**不触碰 `dev_workspaces`**。
- `leave()` 只改 `launchChannel`，不动工作区（`deploy/DevWorkspaceManager.kt:106-111`）。
- `enter()` / `prepare()` 对已存在的工作区分支是 `else -> existing`，**不会无条件重置基线**（同文件 `:78-82`、`:94-98`）。

**⇒ 安装行为本身是安全的。真正的问题只发生在“已经离开开发模式之后又装了包，然后重新打开开发模式”这一刻。**

### 4.2 需要的三个量已经有两个

- `dirty`：开发树相对基线是否变过。算法为 `treeHash != getRelease(baseReleaseId).treeHash`（`deploy/DevWorkspaceManager.kt:440-443`），并已在 `model/DevWorkspace.kt:21` 输出。
- `baseOutdated`：设备正式版相对基线是否换过（`model/DevWorkspace.kt:22`）。
- **`matchesActive`：开发树内容是否等于设备当前正式版内容 —— 目前没有算。**

### 4.3 现存三处需要修改的地方

1. **`haminn-agent.py:854-856`** 用 `versions_differ`（版本号）作为判据，在 `:873-875` 决定非交互时 `raise` 还是继续。这是全仓唯一用版本号做覆盖判断的地方，必须换掉。
2. **`deploy/DevWorkspaceManager.kt:65-69` 与 `:99-103`** 的 `state` 取值里 `base-outdated` 优先于 `dirty`，把“双方都动过”和“只有设备动过”压成同一个字符串。判定方据此无法区分，只能退回版本号猜。
3. **`haminn-agent.py:970-972`** promote 到 stable 的守卫只有 `version.code <= active.versionCode`。本地第三段持续 +1 就会绕过它，导致覆盖别人的包且无人被问。推的方向需要与拉的方向用同一套判定。

## 五、判定表

记 `H_dev` = 开发工作区内容指纹，`H_active` = 设备当前正式版内容指纹，`Published` = 本机发布过的指纹账本（第六节）。

| 情况 | 含义 | 动作 |
| --- | --- | --- |
| 本地没有该 happ 的开发工作区 | 没有可丢的内容 | 从 `H_active` 新建，**不问** |
| `H_dev == H_active` | 两边就是同一份 | 直接对齐基线，**不问** |
| `H_dev != H_active`，且 `H_dev` 相对基线变过、`H_active` 没变 | 只有开发端在动 | 直接推，**不问** |
| `H_dev != H_active`，且 `H_dev` 没变、`H_active` 变了 | 只有设备动过 | 自动跟随 `H_active`，**不问**（现有 `rebuild` 已实现） |
| `H_dev != H_active`，两边都变过，且 `H_active ∈ Published` | **设备上那份是本机自己发出去的** | 继续以开发端代码为基础开发，**不问** |
| 其余 | 外部塞进来的包 + 本地有未落定改动 | **问，两选一**（第七节） |

第五行是必需的一条：它管住“我发布了包 P，又在本地接着改到 Q，设备上仍是 P”这个场景。此时两个指纹不相等，按“只比是否相等”会误问；但 P 是本机发出的，开发端必然比 P 新，所以直接以开发端为基础继续即可。

判定以**设备端开发工作区的 `tree_hash`** 为准，不另行读取本地目录。本地目录的改动会在同步时进入工作区，归属“只有开发端在动”那一行。

## 六、已发布指纹账本

本机需要记住自己发出过哪些包，用于判定表第五行。

- **内容**：每个 happId 对应一串内容指纹。
- **上限**：不设上限，或上限 1024 条。只是搜索时用的一条记录，空间与性能都可以忽略。
- **写入时机**：`promote`（`update-dir`）成功、正式 package 成功之后追加。
- **存放位置**：开发端（`~/haminn/happ-dev.json` 的既有 happId 条目内扩展字段，或同目录独立文件）。读取时需兼容旧结构（旧值可能是纯目录字符串）。
- **不记“人”**，只记指纹。理由见第三节。

**刻意的性质**：这是一份本机账本。换机器、重装开发端之后账本为空，第五行不再命中，全部分叉都会走到“问”。这个降级方向是正确的、保守的。

## 七、询问与处置

### 7.1 触发条件

**只在判定表最后一行触发**，即：本地已有该 happ 的开发工作区，且开发端与设备正式版都已偏离基线，且设备上那份不是本机发出去的。

本地没有工作区时不问 —— 没有可丢的内容。

### 7.2 两个选项

- **A. 备份本地开发工作区，改用设备上的新代码重新开发。**
  备份是 A 的内置步骤，不是一个可选分支。备份完成后把工作区重置到新的正式版（现有 `reset()`，`deploy/DevWorkspaceManager.kt:113-121`）。
- **B. 继续用本地开发工作区开发，完全不理睬设备上装了什么。**

没有第三个选项。不做自动合并；本来也无从判断“该保留哪边”。

### 7.3 界面

**本判定不新增界面。** 界面就是宿主向用户展示参考信息并询问怎么处理。

宿主弹窗展示两栏，另加两个按钮：

- **【本机核实】设备上现在这份**：指纹前几位、体积、文件数、安装时间、来源通道。
- **【本机核实】本地开发工作区**：指纹前几位、最后改动时间、文件数。
- **【打包者声明·未核实】设备上那份自带**：作者、打包日期、基于哪一版。
- 按钮：**备份本地并改用设备上的新代码** / **继续用本地代码，不动设备**。

第三栏必须显式标注“未核实”，不得与本机核实的信息混排，避免时间一长被当作事实。

### 7.4 避免反复询问

要求宿主尽可能建立良好机制，**只在关键变更、可能导致用户开发内容自动丢失时才询问**。

- 把已作出的决定**绑定到 `(H_dev, H_active)` 这一对指纹上**。同一对指纹不再询问。
- 开发端内容再变，或设备正式版再换，就是新的分叉，重新询问一次。
- 正常开发过程（第五行以前的各种情形）一律静默处理，不产生任何提示。

### 7.5 备份

- 本计划中的“备份”一律指**备份本地开发工作空间**。
- **备份的具体实现留给宿主自行解决**：怎么备份、存在哪、保留几份、用什么格式，都由宿主与开发者自行决定。
- 只提出一条要求：**备份必须是可回退的** —— 用户能够凭它把开发内容取回来。
- 设备侧的正式版内容是内容寻址且不可变的，换版只是改 `active_release_id` 指向，不会被删除，因此**不需要为它做备份**。真正需要保护的只有本地那一份。

## 八、happ 打包元信息规范

### 8.1 定位

发布包默认要携带一组自述信息，**唯一用途是在第七节那次询问发生时提供参考**。

**这组信息一律不可信，不参与任何自动判定、不参与任何覆盖决定**（见第三节）。它存在的意义是让用户在询问时看到“设备上这份是谁、什么时候、基于什么改的”，而不是只看到两串指纹。

### 8.2 默认必带的字段

| 字段 | 含义 | 取值来源（按优先级） |
| --- | --- | --- |
| `author` | 原作者 | `haminn.json` 的 `author`（已有字段） |
| `maintainer` | 本次打包的更新者 | 命令行参数 → `haminn.json` 的 `maintainer` → **系统当前用户名** |
| `packagedAt` | 打包日期 | 打包工具自动填，ISO 8601 UTC |

**`maintainer` 取不到时必须主动问用户。** 系统用户名不可用（拿不到登录名、为空、或为 `root` / `unknown` 一类无意义值），且既没有参数、也没有清单声明时，打包工具应当**停下来询问**，不得静默留空、不得编造。同时提供 `--maintainer` 之类显式入口供自动化使用。

### 8.3 可选的来源信息

`basedOn` 描述本包基于哪个包开发，内容是该父包的同一套字段：

```json
{
  "name": "HamDraw",
  "happId": "life.airen.hamdraw",
  "versionName": "0.5.40",
  "versionCode": 118,
  "author": "zhyuzh",
  "maintainer": "zhyuzh",
  "packagedAt": "2026-09-20T08:12:00Z"
}
```

父包自身若也带了 `basedOn`，打包工具应当继承，形成一条从本包往回的链，并设深度上限（建议 8 层），超出即截断，避免包体膨胀。

### 8.4 包里不放指纹

**包内不得写入任何形式的内容指纹声明**，包括 `basedOn.treeHash`。

两条理由：指纹只有在包生成之后才算得出来，写进去会让包内容变化、指纹再变，形成死循环；而且写进去的指纹本来也不可信。

**指纹一律由接收方 haminn 自己计算**（第三节）。这也正是“判断是不是自己发布的包”只能靠本机账本、不能靠包内声明的根本原因。

### 8.5 放在哪里

推荐在包根放一个**独立的可选文件 `haminn-build.json`**，与 `haminn.json` 并列。

- 这些字段每次打包都变（日期、基于哪个包），写进会提交进仓库的 `haminn.json` 会污染源码、产生无谓 diff；
- `haminn.json` 定义的是包的身份（happId / name / version），构建元信息不属于身份；
- 与既有做法一致：`haminn-install.json` 同样是“只在出包时才动”的独立文件。

`maintainer` 建议同时作为 `haminn.json` 的可选字段声明，作为稳定落点；打包工具在没有参数时优先读它。`haminn.schema.json` 需相应放宽（当前 `additionalProperties: false`）。

**文件缺失时安装方直接跳过**：不影响安装、不影响判定，只是询问时少显示一栏。

### 8.6 安装方要做什么

- 读取 `haminn-build.json`（存在时），**只作展示**；
- 随 release 一起留存（存进 release 记录的一个声明字段），供后续询问时取用；
- **不得**用它做任何自动决定；
- 界面上必须与“本机核实”的信息分栏，并标注**未核实**（见 7.3）。

## 十、验收标准

1. 本地没有开发工作区时，打开开发模式不产生任何询问。
2. 只有开发端改动时，同步静默完成，不产生询问。
3. 只有设备正式版被换（开发端没改）时，工作区自动跟随新正式版，不产生询问。
4. 本机发布过包 P 后在本地继续改到 Q、设备上仍是 P 时，不询问，直接以本地代码继续。
5. 本地有未落定改动 _且_ 设备上装进了非本机发布的包时，询问一次，且给出 7.3 的两栏信息。
6. 对同一对 `(H_dev, H_active)` 不重复询问；任一侧再变时重新询问。
7. 选择 A 时，本地开发工作区在重置之前已完成可回退的备份。
8. 选择 B 时，设备上那个包不被删除（仍可在 `releases` 中找回），本地工作区不受影响。
9. 任何路径下，都不存在“因版本号比较而自动覆盖用户开发内容”的行为。
10. 包内的声明信息在界面上始终标注“未核实”，且不参与任何自动决定。
11. 打包时更新者姓名的所有来源都拿不到时，打包工具**停下询问**，不静默留空、不编造。
12. 包内不含任何形式的内容指纹声明；`basedOn` 链深度不超过 8 层。
13. 缺少 `haminn-build.json` 的包能正常安装、正常开发，只是询问时少显示那一栏。

## 十一、明确不做

- **不做自动合并**，也不做服务端逐文件 diff 或冲突裁决。
- **不做版本号优先覆盖**，任何覆盖决定不得以版本号为依据。
- **不做“回退到历史版本重新开发”这门功能** —— 那是宿主（HaminnApp）自身的能力。用户若要强行回到老版本开发，应自行解压旧代码并由宿主完成替换，本计划只负责识别分叉并提示，不提供该流程。
- **不规定备份的实现方式**，只要求可回退。
- **不采信包内的任何自述信息**用于自动判定。
- **不因为安装行为本身做任何拦截**：安装始终是安全的，判定只发生在重新打开开发模式、或向正式版发布之前。
